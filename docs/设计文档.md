## 0. 设计目标与约束

| 目标 | 落到设计上的含义 |
|---|---|
| 离线可读 | 无服务端、无构建期运行时依赖；`file://` 双击可开 → 数据内联进 HTML（规避 CORS） |
| 可追溯 | 锚点存「段落 ID + 段内偏移」，不存全文偏移（段落是稳定坐标系） |
| 身份随时间变 | 人物身份拆成 `person_tenure` 时间片表，而非 person 上的单一字段 |
| 地理正确 | 经纬度在构建期投影成像素，前端不做投影；州界靠拓扑共享而非各自描边 |
| 一处逻辑只有一份 | 地图抽成 `app/map_core.js`，构建期内联；回归脚本机械校验同源 |
| 可增量铺量 | 新增回目 = 加数据文件 + 加一条索引，不改渲染代码 |

三条**不可违反的硬约束**（写在 `map_core.js` 头部，改代码前必须先读）：

1. **屏幕像素恒定**：观感尺寸不随缩放变化的元素（选中靶心、战线节点），一律用 `data-sz` 声明「屏幕像素」，再由 `applySpacing(root, pz)` 按 `1/pz` 折回画布单位，且动画每帧都要重新 apply。
2. **`pz ≠ z`**：屏幕真实倍率 = `z × clientWidth / C.w`。所有注记字号与显隐阈值按 `pz` 算，否则卡片内嵌小图（宽 300px 左右）的标签会缩成看不见的点。
3. **前端不做投影**：`data/geo-real.json` 里已是像素坐标，前端只负责画。

## 1. 总体架构

### 1.1 构建期 / 运行期分离

```
构建期（Python，跑一次）                      运行期（浏览器，零依赖）
┌──────────────────────────────┐            ┌───────────────────────────┐
│ data/*.json  data/source/*.txt│            │ app/reader.html（11.4MB） │
│  (persons×25, ch001–120.txt)  │            │  └ 内联：DATA + MapCore    │
│         ↓                     │            │  └ 外链：assets/terrain.jpg│
│ scripts/build.py              │  内联注入   │                           │
│  ├ 词表编译 → 段落扫描         │ ─────────→ │ app/map_test.html（调试页）│
│  ├ 锚点/卡片/事件/大势组装     │            │                           │
│  └ _write_app() 模板替换       │            └───────────────────────────┘
└──────────────────────────────┘                     │ 静态托管
        ↑                                            ↓
   scripts/prepare_geo.py              https://zhujiu.app.workbuddy.host
   scripts/build_terrain.py           （index.html + assets/terrain.jpg）
   scripts/build_power.py
   scripts/expand_persons.py          （自动铺量建档，批产期）
   scripts/fix_tenure_span.py         （任期/阵营批量修复，批产期）
```

**为什么不留一个 HTTP 服务**：需求 NF-1 要求断网可用、拷给别人能开。`file://` 下 `fetch()` 会被 CORS 拦住，所以数据必须内联。代价是单文件体积（见 §9）。

**为什么还保留 `map_test.html`**：它是地图调参台（注记阈值、选中态、战线节点都在这里先调），同时是回归的独立样本。两页共用同一内核，所以调完不需要再改阅读器。

### 1.2 构建期任务顺序

`build.py:main()` 的顺序有依赖关系，不可随意调换：

1. 载入 `chapters.json` → 逐回读 `data/source/chNNN.txt` → 按空行切段（段落是锚点坐标系，必须先定）。
2. `load_rules()` 编译 `lexicon-rules.json`；`apply_single_char()` 生成单字闸门；`build_lexicon()` 产出 `{surface: [(type,id)]}`。
3. 逐段 `match_paragraph()` 扫描 → 命中后 `resolve_anaphora()` 做同段回指消歧 → 产出 mention 列表。
4. 载入人物卡 / 地名（种子 CSV + 增量 JSON），计算全书提及次数、像素坐标。
5. 载入事件与战役，解析 `passage_ids` 的（回数 + 关键词）→ 真实段落 ID。
6. `build_power.build(persons, events)` 展开大势年份（依赖人物 tenure 与事件年份）。
7. `_write_app()` 把 DATA 与 MapCore 内联进两个模板 → `app/*.html`。

### 1.3 目录职责

| 路径 | 职责 | 谁写 |
|---|---|---|
| `data/source/chNNN.txt` | 纯正文，不含回目/站点信息 | 抓取脚本 → 人工校验 |
| `data/chapters.json` | 回目索引（no/title） | 人工 |
| `data/persons_*.json` | 人物卡，按批次分文件 | 批产 + 人工校 |
| `data/places-seed.csv` / `places-additions.json` | 地名种子 / 后补点 | 人工 |
| `data/event_battle_*.json` | 事件与战役 | 脚本生成 + 人工校 |
| `data/power.json` | 势力定义 + 州归属快照 | 手工考据 |
| `data/geo-real.json` | 底图几何（像素化前的经纬度） | `prepare_geo.py` |
| `data/entity-schema.json` / `lexicon-rules.json` | 约束与规则 | 人工 |
| `app/map_core.js` | 地图唯一实现 | 人工 |
| `app/*_template.html` | 页面模板（不含数据） | 人工 |
| `build/` | 产物与缓存 | 脚本（可删） |

## 2. 数据层设计

### 2.1 概念模型

```
chapter 1 ──n passage 1 ──n mention n──1 person / place / event
                                 │
person 1 ──n person_tenure n──1 faction
person 1 ──n timeline_node           event 1 ──n battle
place  1 ──n timeline_node           battle 1 ──n front_line（JSON 数组，非表）
```

`entity-schema.json` 定义 10 张表的字段、必填性与 9 组枚举，外加 5 条全局校验规则：

1. 所有 mention 的 `entity_id` 必须能解析到 person/place/event；
2. `person_tenure` 时间片并集应覆盖主要活动期，不留无解释空档；
3. `battle.front_line` 的像素坐标必须落在同一 `tile_sheet` 内；
4. `review_status = verified` 的记录 `basis` 不得为空；
5. 批产中 birth/death 出现推测值必须置 `null` 且 `date_precision = unknown`。

### 2.2 五个关键建模决策

**(a) mention 用「段落 ID + 段内偏移」，不用全文偏移。**

全文偏移的脆弱点：任何一次改字（补标点、修错字）都会让其后所有锚点位移，而位移是静默的——页面不会报错，只会链错人。用段内偏移，修改一段只影响该段。schema 里为此写明「passage.text 发布后不可修改，修改必须走版本迁移并重算其下所有 mention 偏移」。

记录形如：

```json
{"passage_id": 30001, "start": 2, "end": 4, "surface": "袁绍",
 "entity_type": "person", "entity_id": "yuan_shao",
 "source": "dictionary", "confidence": 0.99, "is_weak_link": false}
```

**(b) 人物身份是时间片表，不是字段。**

`person_tenure` 每行 = 一段「在哪个阵营、什么身份、事谁、什么官职、从哪年到哪年、依据是什么」：

```json
{"faction_id": "warlord", "role": "武将", "start_year": 184, "end_year": 200,
 "lord_id": "liu_bei", "title": "别部司马、下邳太守（皆刘备所署）",
 "basis": "第一回随刘备讨黄巾；刘备为群雄期间关羽为其部曲将领。", "confidence": 0.9}
```

若把阵营做成 `person.faction` 单字段，关羽只能被标成蜀汉——而蜀汉 221 年建立，关羽 220 年已死。这是「一人一阵营」模型的必然错误，不是数据瑕疵。

**(b2) 任期结束年不得取「势力年份上限」。**

自动建档（`expand_persons.clamp_tenure`）曾把结束年一律设成所属势力的年份上限：

```python
lo, hi = FAC_BOUND[fac]
s = max(lo, min(CH_YEAR[first_ch], hi))
e = hi          # ← 与本人何时退场无关
```

于是左丰——只在第 1 回索贿卢植、全书出现 2 次——因为阵营被判成 `barbarian`（上限 280），
在人物页 184–280 的每一年都「在任」。全书 **310 片**如此（368 片吃满上限，扣除人工
核过的与追谥类）。

现以**末见回目**（正文中最后一次被锚点命中的章 → 换算出年份）作为结束年，由
`scripts/fix_tenure_span.py` 收敛。两条排除：

- **只动 `review_status == 'auto'` 的片**，人工核过的不动（他们多半有史实卒年依据）；
- **跳过「追谥」**——曹嵩 `wei/追谥 220–266` 是曹丕称帝后追尊，本就晚于其 194 年阵亡。

偏差以低估为主（顾雍末见 229 / 史实卒 243，薛综末见 208 / 史实卒 243），因为「演义里
戏份结束」早于「史实寿命」——对「在任时间片」这个语义，这恰恰是对的估计。反方向（被
身后追述，如陆逊末见第 119 回 = 264、史实卒 245）是安全方向。

防回归：`verify.py` 有「自动建档任期不晚于末见回目」一项，判据即上述口径。

**(c) faction 有两个起始年。**

`start_year`（国号年，曹魏 220）与 `de_facto_start`（势力形成年，曹操 196 迎献帝都许）。时间片校验下限用 `de_facto_start`，否则关羽这类「卒于建号前」的人会无处归属。

**(d) 生卒年精度显式建模。**

`date_precision ∈ {exact, approx, unknown, disputed}`，前端只显示后三档的标记（exact 不显示，避免满屏噪声）。批产时模型不确定必须输出 `null`，禁止推测——这条是全局校验规则第 5 条。

**(e) 强弱链接分离。**

`is_weak_link = true` 的锚点按设计是「照样高亮，但只给提示、不弹卡」——证据不足以撑起一张确定的卡，弹全卡等于撒谎。

> **实测更正（2026-10-27 23:40）**：本节此前把弱链接描述为「官职代称『丞相』『都督』」，**与数据不符**。
> 实测 74 条 `is_weak_link` **全部**是 `source = anaphora` 的回指推定锚点（九个单字：嵩/进/让/信/表/良/汜/融/攸），
> 「丞相」「都督」「大将军」「主公」被链接处均为 **0**。官职代称通道目前并未产出任何弱链接，属「尚未实现」而非「已实现待接」。

两类标记的分工（前端已按此实现，`reader_template.html`）：

| 标记 | 数据来源 | 含义 | 样式 | 点击 |
|---|---|---|---|---|
| `.weak` | `source === 'anaphora'` | 回指推定，**推定过程可解释**（同段前文有全称） | 虚线 + 略淡 | 正常弹卡 |
| `.wl` | `is_weak_link === true` | 证据不足，**推定结果不可靠**（如同段「嵩」对应曹嵩/皇甫嵩两人） | 点线 + 更淡 | 只浮一句提示，不弹卡 |

`is_weak_link` 优先级高于 `anaphora`：一条锚点若两者兼具，按弱链接处理（宁可不弹，不可弹出错误的人）。

### 2.3 阵营 id 与显示名分离

Schema 的枚举用中文名（东汉/群雄/曹魏/孙吴/蜀汉/晋/异族/神怪），实现里 id 用英文 slug，显示名与配色集中在 `build.py:FACTION_META`：

```python
'han': ('东汉', '#8a7a5c'),   'warlord': ('群雄', '#7d7d7d'),
'wei': ('曹魏', '#2f5673'),   'wu': ('孙吴', '#3f6b4f'),
'shu': ('蜀汉', '#9c2b1f'),   'jin': ('晋',   '#6b4e7d'),
'barbarian': ('异族', '#8a6a3a'), 'mystic': ('神怪', '#5d4a72'),
```

好处：URL/JSON/文件名里没有中文（避免编码问题），改名只改一处。代价：schema 与实际数据之间多一层映射，读数据时要查表。

### 2.3.1 阵营是怎么定下来的（三级来源，两级会错）

| 级 | 来源 | 覆盖 | 可信度 |
|---|---|---|---|
| 1 | `data/faction_roster.json` | 412 人 | 高（人工整理） |
| 2 | `infer_from_note()` 按抓取源注记的关键词推断 | 自动铺量卡（`expand_persons.py`） | 中，**会出错** |
| 3 | 兜底 `warlord` / `mystic` | 少量 | 低，明确标记 `confidence: 0.35` |

第二级有四个已踩过的坑，改关键词前必读：

- **注记自我印证**。`note` 既直接作为 `summary` 展示，又是推断的唯一依据。抓取源把左丰写成「异族文臣，黄门」——他实为十常侍一党、汉廷宦官——推断照抄成了 `barbarian`。这类错**无法靠改关键词修**，只能按正文改判（`fix_tenure_span.py` 的 `REFACE` 表）。
- **关键词过宽**。裸词 `司马` 本意是「司马氏」，实际命中了「大司马」这个官职：吴大司马吕岱因此被判成魏。现改为只认 `司马懿|司马师`。
- **分支顺序即优先级**。`晋` 分支排在 `魏` 之后、而 `魏` 含 `司马` 时，「司马昭」永远先命中魏，晋分支不可达。`晋` 现置于 `魏` 之前。
- **家族语境误伤（马肃案例）**。马腾之父马肃是「演义未载」的正史补录卡，注记写「与羌人杂处，遂娶羌女生腾」——`羌` 关键词命中异族分支，但马肃本人是东汉县尉，「羌」说的是其媳血统与居地。**家人语境里的族群词不构成本人阵营依据**，此类卡一律人工改判（已改 `han`，任期按桓帝朝 147–167 收敛）。

判错的代价不只是颜色：`clamp_tenure()` 按阵营的年份上下界截任期，阵营错 → 年份也错（左丰 184–280 全程在任的根因之一）。所以 `verify.py` 有一条交叉校验：**简介职任段若写「魏司徒」「吴大司马」，该政权必须出现在本人的 `tenure.faction_id` 里**。判据取职任段前两字「阵营字 + 官职字」——加「官职字」是因为「魏延追赶不上」的「魏」是人名；职任段横跨两朝时（贾逵「汉谏议大夫，魏建威将军」）任一匹配即通过。

## 3. 构建管线

### 3.1 词表编译：`RuleSet`

`lexicon-rules.json` 的规则被编译成三个查询结构：

| 操作 | 语义 | 例 |
|---|---|---|
| `deny` | 该表面形式全书禁用 | 「进」「让」「吴」作为单字不链 |
| `drop` | 从某实体移除某表面形式 | 「荆州」不属于江陵这个点 |
| `guard` | 给某实体某表面形式加上下文闸门 | `mode=guarded` 必须 `allow_prev` / `allow_next` 命中才匹配 |

`allow()` 是扫描时唯一入口，返回布尔。当前 **67 条规则、2,335 个表面形式**。

> 经验数据：这 20 条规则**全部来自第 1–3 回**。第 4–10 回（36,951 字，是前 3 回的 2.4 倍，含界桥、宛城、下邳等新场景）新增 **0 条**——说明是机制收敛而非词表膨胀，剩余回目可以直接跑。

### 3.2 贪心最长匹配

```python
for L in range(min(max_len, n - i), 0, -1):        # 从最长形式开始试
    for (etype, eid) in cands.get(text[i:i+L], ()):
        if rules.allow(etype, eid, seg, text, i, i+L):
            hit = ...; break
```

关键点：候选被规则拦下时**继续尝试更短的形式**。例：遇到「中山靖王」时「靖」被拦，但整串仍能命中刘备的别名链，不会因为长形式被拒就整段放弃。

### 3.3 单字通道（末字单称）

演义里最常见的指代是「名末字 + 曰/怒/大喜」：`绍曰`、`操大怒`。规则：

- 仅对「姓名末字全书唯一对应一人」的字自动启用（实测 106 个末字中 6 个歧义、14 个禁用）；
- 前置条件：前一字为标点/空白（或段首）**或**言语动词（`卓问肃曰` 的「肃」前是「问」）；
- 后置条件：后接词必须命中 `allow_next`（言语/动作动词表）。

两个条件并存。`apply_single_char()` 直接把这些闸门写进 `rules.guards`，扫描逻辑因此不需要分支。

### 3.4 同段回指消歧

解决两类歧义：末字对应两人以上（良 → 颜良/蒯良、嵩 → 皇甫嵩/曹嵩），或末字唯一但该字本身是高频动词/名词（表 → 上表、信 → 书信）。

三条件同时满足才链接：

1. 前接标点为界（或言语动词）；
2. 后接言语类动词——「表为荆州刺史」因后接「为」自动出局；
3. 同段之内该字之前刚出现过结尾相同的**全称**，且最近的只有一个。

只做段内（`window=passage`）。跨段回指需要篇章级共指，误配代价远高于漏链。

### 3.5 事件与战役生成器

`gen_events_pXXX.py` 模式：把「回数 + 关键词」写成声明式表，脚本去原文里找，找到就解析成真实 `passage_id`，找不到**断言失败**。

```python
PASSAGES = [(25, '青梅'), (25, '惟使君与操'), ...]   # 关键词必须是原文实际措辞
```

> 这个设计反复救过命：手填 `passage_id` 时，正文重新分段就会静默错位；用关键词解析，措辞对不上会立刻炸。踩过的坑是关键词写成了概括语（「煮酒论英雄」）而不是原文措辞（「青梅」），命中 0 条。

### 3.6 模板注入

```python
core = open(APP/'map_core.js').read()
tpl  = open(APP/tpl_name).read()
if '/*__MAPCORE__*/' not in tpl:
    raise SystemExit('模板缺少 /*__MAPCORE__*/ 占位符：' + tpl_name)
html = tpl.replace('/*__MAPCORE__*/', core).replace('/*__DATA__*/null', json.dumps(data, ensure_ascii=False))
```

缺占位符直接 `SystemExit`，而不是静默产出半成品——这是「双轨漂移」的机制化防线。

## 5. 地图内核 MapCore

### 5.1 分层与裁剪

`drawBase()` 按绘制顺序建 8 层，返回引用对象供后续调样式：

```
clipPath(画布矩形)
└ base(g, clip)
  ├ 地形 image 或 海岸线 path
  ├ zhoupoly  州界：米白晕底(3px) + 淡紫虚线(1.1px, 7 6)
  ├ 水系（rivers + lakes）
  ├ 州名 text（26px 衬线、字距 4、米白描边）
  ├ 汉县点（郡治 2.6 / 属县 1.7，两层半径）
  ← 以下在 clip 外（注记要能压到边缘）
  ├ capLb  郡国治所名
  ├ cntLb  属县名
  └ wlb    水名
```

返回 `{base, zhouPoly, zhouLb, ctyDots, capLb, cntLb, wlb}`，即 `svg._refs`。

州界与州名用 `vector-effect: non-scaling-stroke`：描边宽度不随 viewBox 放大，省掉每帧折算。

### 5.2 坐标与投影

画布 1400×1200，覆盖 `lng 97–126, lat 18–44`。投影为**等距圆柱 + 中纬余弦压缩**：

```python
_COS = cos(radians((18+44)/2))          # ≈0.83
_K   = min(w / ((lng1-lng0)*_COS), h / (lat1-lat0))
project(lng, lat) = ((lng-lng0)*_COS*_K + offX, (lat1-lat)*_K)
```

不用 Web Mercator：跨度只有 18°–44°，等距圆柱的形变在可接受范围，且「1 像素对应多少度」保持线性，坐标核对时心算得出来。

### 5.3 感知缩放 `pz`

```js
function displayZoom(svg, C, z) {
  var w = svg.clientWidth || 0, h = svg.clientHeight || 0;
  if (w < 8) w = C.w;          // 隐藏视图尚未布局时退化
  if (h < 8) h = C.h;
  // meet 下真实缩放 = min(W/vw, H/vh)；只看宽度会在扁长容器里高估
  return z * Math.min(w / C.w, h / C.h);
}
```

同一份数据渲染到 1400px 主图和 654×228 的卡片小图：主图 `z=1` 时 `pz≈1`，卡片按画布比例取景时 `pz≈0.31`。若字号写 `26/ z`，小图上就是 84 画布单位——屏幕上仍是 26px 吗？不是，是 26×0.31=8px，看不见。所以一切除以 `pz`。

卡片小图的取景框宽高比与容器一致，此时 `meet` 的 `min(W/vw, H/vh)` 两值相等，`pz` 精确等于「容器像素 / 取景框画布单位」；`cardFrame` 把取景框当成临时画布喂给 `decorScale(refs, svg, {w:vw, h:vh}, 1)`，正是为了拿到这个精确值。

### 5.4 注记分级阈值

`decorScale(refs, svg, C, z)` 每帧执行：

| 元素 | 显隐条件 | 字号 |
|---|---|---|
| 州名 / 州界 | `pz ≤ 2.5` 全显，之后线性淡出（`zf = max(0, 1-(pz-2.5))`） | 26 / pz（恒定屏幕 26px） |
| 水名 | `pz ≥ 2.0` | `min(26, 8√pz+4)` / pz |
| 郡治名 | `pz ≥ 2.6` | `min(30, 9√pz+4)` / pz |
| 属县名 | `pz ≥ 5.0` | `min(26, 8√pz+4)` / pz |
| 县点半径 | 始终 | 郡治 2.6 / 属县 1.7，除以 pz |

字号用 `√pz` 而非线性：放大 4 倍时字只长大 2 倍，既看得清又不会一屏挤出二十个大字；再加屏幕上限兜住极端值。

### 5.5 屏幕像素恒定协议

元素上用 `data-*` 声明「屏幕像素」，由 `applySpacing(root, pz)` 统一折算：

| 属性 | 含义 |
|---|---|
| `data-sz` | 屏幕像素尺寸：text→font-size、circle→r、其余→stroke-width |
| `data-stroke` | circle 的描边宽（屏幕像素） |
| `data-halo` | 文字描边（米白光晕）宽 |
| `data-dash` | 虚线（`"9 7"`，逐段折回） |
| `data-ax/ay` | 锚点绝对坐标（**不折算**，仅作基准） |
| `data-dx/dy` | 相对锚点的屏幕像素偏移（折算） |

```js
x = data.ax + data.dx * k;    y = data.ay + data.dy * k;    // k = 1/pz
```

分开写 `ax` 与 `dx` 是关键：如果直接改 `x`，下一帧再折算就会在已折算的值上再折一次，缩放动画里节点会一路漂走。

### 5.6 视图状态机 `createView(svg, C, opt)`

```js
V = {cx, cy, s}                      // 中心 + 比例，s ∈ [min=1, max=14]
apply()      // 算 viewBox、算 pz、跑 onApply 钩子、更新比例读数
clamp()      // 中心夹在有效范围；s 到下限时强制回中
animateTo()  // s 走对数插值（视觉匀速），cx/cy 线性；缓动 1-(1-k)^3
zoomAt(px,py,f) // 以鼠标处为不动点：cx = px - (px-cx)*(s1/s)
bind(ids)    // 滚轮/双击/拖拽/＋－/复位
```

两个细节：

- **钩子归一化**：`onApply` 允许传单个函数或数组（`hooks = Array.isArray(opt.onApply) ? opt.onApply : [opt.onApply]`）。这个 bug 曾让地图页深链静默失效——传单个函数时 `hooks.length` 为 undefined，循环不执行，`apply()` 什么都不做。
- **用 `on*` 属性而非 `addEventListener`**：同一张图重复渲染（切视图回来）时不会叠加监听器。

### 5.7 选中态：靶心 + 米白名牌

`makeFocus(layer, C, getPz, refs)` 返回 `{add, clear, place, items}`。单个标记由四件组成：

| 元素 | 尺寸（屏幕像素） | 说明 |
|---|---|---|
| halo | r=14，`fill-opacity .1` | 淡晕 |
| ring | r=14，`opacity .62`，stroke 1.1 | 细环（靶心） |
| dot | r=3.4 | 中心点 |
| plate | 圆角矩形 + 文字 | `#f8f3e7` 底、字色跟随标记色、14px serif 600 |

名牌布局算法（`place(pz)`，每帧重算）：

```
w = textW(name, size) + 2*padX;  h = size + 2*padY
below  = y + R + gap + h <= C.h - 2k          // 默认挂下方
by     = below ? y + R + gap : y - R - gap - h  // 贴下缘翻上方
bx     = clamp(x - w/2, 2k, C.w - w - 2k)      // 左右夹回画布
```

`add()` 同时调用 `dimSame(name, true)`：把底图同名注记 `opacity` 直接置 0。
> 试过置 0.15，仍有淡淡重影压在水系上，看起来像渲染故障。**完全隐藏**才对。

### 5.7.1 四种高亮的视觉语言

同一张图上可能同时存在四种「选中」，必须一眼可分：

| 对象 | 语言 | 取景 |
|---|---|---|
| 州 | `#7d1f16` 实线 2.4 + 米白晕底，州名 34 / 700 | 州名锚点，固定 1.9× |
| 郡 | `#c2641f` 实线 1.6，郡名 18 / 700 | 郡外接框质心，2.6× |
| 地理分区 | 青灰 45° 斜纹填充 + `#2f5153` 虚线界 + 34px 青字 | 分区外接框，1.4–2.4× |
| 水系 | 底图河线加粗：深蓝 `#15659e` ×1.5 线宽 + 浅蓝晕边 ×3 线宽 | 水体外接框，`fitZoom()` 1–6× |

水系高亮的描边**不带** `non-scaling-stroke`：底图河宽是画布单位、随缩放变粗，高亮若写固定屏幕像素，放大到 3× 时反而比底图河线更细（等同没高亮）。取景比例由 `fitZoom(C, xs, ys, {pad, minSpan, maxZ})` 按外接框算，不再按类型写死 1.2×——长江横跨半图、汉水只占一块，同一个数字必然一头看不到尾、一头漂在空白里。

## 6. 州界拓扑算法（`prepare_geo.py`）

### 6.1 为什么要共享

十三州边界是**同一批地理边界的两侧**。手工为每州各描一遍，必然出现三类病：

1. 两州控制点差 0.1–0.22°，缝隙肉眼可见；
2. 公共边界的中间路径各描各的，错开最大 1.5°（益州—荆州曾如此）；
3. 各自闭合后独立平滑，外推方向不同，接缝处一个向内一个向外。

结论：**贴合不能靠描得像，只能靠同一份数据**。`HAND_ZHOU` 把 17 对相邻边界写成「两州共用同一串控制点、方向相反」。

### 6.2 六步流水 `build_zhoupoly()`

```
① _align_zhou_pts(rings, tol=0.25)   跨州点聚类对齐（并查集，同簇取均值）
② 环按共享节点拆段                   每段有明确的 (起点, 终点, 用户集合)
③ 同端点对段归并                     路径不一致时取更密的一方
④ 弧合并                             users 相同且几何相接的相邻段合并成一条弧
⑤ 每弧 _smooth_open 平滑一次          含起点不含末端（避免端点外推）
⑥ 每州按几何链动态排序拼接            环闭合断言 → 输出
```

第 ⑥ 步是两个 bug 逼出来的：

- 弧合并会打乱环的原始 `seq` 顺序，按 seq 拼必然错位 → 改为按几何链（谁的终点接谁）动态排序；
- 环的起点有两个可选方向，取正向弧的起点，反向弧要 `append(v) + reversed(sm)[:-1]`（否则丢终点）。

### 6.3 五个坑（都踩过）

| 坑 | 现象 | 修法 |
|---|---|---|
| `_smooth_open` 退化段返回整段 | m<3 时返回含两端的点，与拼接协议冲突（重复端点） | 退化时只返回 `[起点]` |
| 反向弧丢了终点 | `reversed(sm)[:-1]` 用反 | 明确「先补终点再倒序去首」 |
| 正向弧砍掉起点 | `extend(a[:-1])` 少了端点 | 改 `extend(sm)` |
| 兖州多边形自交 | 非零环绕规则下漏填 | 删豫兖界「手枪把」三晃点 + 加 `is_simple` 断言 |
| polygonize 方案崩溃 | `make_valid` 未处理、碎片 <12% | 弃用，回到底层弧方案 |

当前结果：40 条弧 / 17 对公共边界 / 343 个共享点，13 州多边形全部 `is_simple`。

## 7. 大势数据展开（`build_power.py`）

输入：`data/power.json`（42 势力 + 28 快照年 × 124 郡）+ 人物 tenure + 事件年份。

```
snap_years = [184, 189, 190, 192, 195, 196, 199, 200, 202, 205, 208, 209,
              211, 214, 215, 219, 220, 221, 222, 224, 229, 234, 238,
              249, 258, 263, 265, 280]
for y in range(184, 281):
    取 ≤y 的最近快照 → 郡归属
    在位者 = tenure 覆盖 y 且 role ∈ {君主, 皇帝, 权臣}
    事件   = start_year == y
```

三条口径：

- **一郡一主 + 可选次主**：`hold: {势力id: [郡名…]}` 每快照每郡恰一主；`contest: {郡名: 势力id}`
  表示争夺/共存，前端画双色斜纹；
- **落不到人物卡的势力不臆造**：归汉廷（`han`）；
- **非快照年要标注依据**：显示「据 XXXX 年局势」，不假装逐年精确。

### 7.1 画布外的郡：`OFFCANVAS_JUN`

敦煌郡治所 94.66°E、属县渊泉 96.0°E，都在画布西缘 97°E 以外，`build_junpoly.py`
整体移出 Voronoi 剖分。但 `data/power.json` 里它 28 个快照年都有明确归属
（马腾 / 曹操 / 魏 / 晋）。两侧口径不同 → `build_power.py` 的一致性校验恒失败。

**这不是「顺手放宽一下」的事**，因为它导致的后果极隐蔽：`build.py` 里大势生成包在
`try/except` 里只打一行日志，`power=None`，`reader.html` 内联 `DATA.power = null`，
大势页整页空白——而 `verify.py` 当时只检查磁盘上的 `build/power.json`，
`reader_power190` 断言的又是侧栏（侧栏照常渲染），**全部 144 项照旧 PASS**。

定案的口径分工：

| 文件 | 含敦煌郡 | 说明 |
|---|---|---|
| `data/power.json` | ✅ | 史实归属，人手维护，不动 |
| `build/junpoly.json` | ❌ | 没有郡面可画 |
| `build/power.json` | ❌ | 渲染数据，生成时剔除 |

三处共用 `scripts/geo_const.py` 里的 `OFFCANVAS_JUN`，一致性校验一律按
`共同部分 = 全集 − OFFCANVAS_JUN` 比较。

配套的防回归措施（缺一不可）：

1. `build.py` 失败时写 `build/power.error`，日志明说「大势视图将整页空白」；
2. `verify.py` 回读**已构建的 reader.html**，断言内联 `DATA.power` 非 null；
3. `reader_power*` 场景加反向断言 `!大势数据未生成`——断的是渲染结果，不是源码文本。

## 8. 验证体系（`scripts/verify.py`）

### 8.1 四段 147 项

### 8.2 断言设计

- **先剥 `<script>` 再匹配**：本项目的模板与数据全部内联，源码里到处是「冀州」「洛阳」这类字符串。直接 `'冀州' in html` 会 100% 假阳性。判页面前用 `re.sub(r'<script\b.*?</script>', '', html, flags=re.S)` 剥掉。
- **支持反向断言**：`'!1.00×'` 表示「不该出现」。深链是否真的定位了，靠这个判断——初始全图读数就是 1.00×。
- **同源校验用 sha1 比对整段内核**，不是比对文件名或行数。
- **查产物，别只查中间文件**：§7.1 的空白页就是这么漏的——磁盘上的 `build/power.json` 一切正常，坏的是「有没有被内联进 reader.html」这一步。凡「A 生成 B、B 才是用户看到的」这类链路，断言必须落在 B 上。

### 8.3 无头浏览器的三个坑

| 坑 | 现象 | 对策 |
|---|---|---|
| `requestAnimationFrame` 时序不稳 | 深链动画在 `--dump-dom`/`--screenshot` 下拍到中间帧，断言随机失败 | 地图页加 `?snap=1`：`animateTo` 变瞬时落位、战役直接画最终帧 |
| `--user-data-dir` 复用导致进程单例 | 两次调用被并进同一实例，截到上一页的图（曾出现 3.00× 的脏截图） | 每次调用独立 profile 目录（时间戳命名） |
| 冷启动偶发超时 | 首次启动 Edge 偶发 DOM 为空 | 失败重试一次（`wait×2`） |

## 12. 架构决策记录（ADR）

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| 1 | 数据内联进 HTML，不起本地服务 | `file://` 下 fetch 被 CORS 拦；要能拷给别人直接开 | 单文件体积大；数据更新必须重构建 |
| 2 | 锚点用「段落 ID + 段内偏移」 | 全文偏移会因改字静默位移 | 改段落必须重算其下锚点 |
| 3 | 人物身份用时间片表 | 「一人一阵营」会把关羽标成蜀汉（221 年才有蜀汉） | 查询要按年份过滤，前端复杂度上升 |
| 4 | 地图抽成 MapCore 单文件内联 | 两页两份实现导致多轮「改了一处另一处没改」 | 内核改动要重建两页 |
| 5 | 州界用拓扑共享而非各自描边 | 手工描边必然留缝/重叠，且无法收敛 | 边界只能整体调整，不能单独改一州 |
| 6 | 大势用离散快照年，不逐年编 | 史实密度不支持逐年精确，编年等于造假 | 年份细粒度不足，需「据某年局势」标注 |
| 7 | 原生 JS + SVG，不引框架 | 离线单文件、零依赖、体积可控；SVG 便于精确控制屏幕像素 | 状态管理靠手写；无组件复用体系 |
| 8 | 回归走无头浏览器 + DOM 断言 | 只有真跑起来才能发现 `onApply` 这类静默失效 | 无头环境不稳，需 `?snap=1`、独立 profile、重试 |
| 9 | 地形图外置为 jpg | base64 内联会膨胀 33%（4MB → 5.4MB）且阻塞解析 | 文件不能单独拷走（需连 assets 目录） |
| 10 | 阵营 id 用 slug，显示名集中映射 | JSON/文件名不含中文，改名只改一处 | 读数据需查 `FACTION_META` |
| 11 | 单字通道与回指通道并存 | 单字解决「绍曰」，回指解决「良」这类多义末字 | 两套闸门叠加，调试时要分清是谁拦下的 |
| 12 | 关键词解析 passage_ids 而非手填 | 重新分段会让手填 ID 静默错位 | 关键词必须与原文实际措辞完全一致（多次翻车） |
